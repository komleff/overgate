## Решение по commit tier (HOW, PM)

Commit tier = **ядро пути коммита**: тесты того, без чего агент не может безопасно коммитить —
структура reference, диспетчер, guard, classifier, гейт коммита, хук готовности PR, launcher
Python, граница уровней:

`structure`, `structural-mutations`, `closure-mutations`, `pre-bash-dispatch`, `portability-names`,
`activation`, `mutation-guard`, `classifier`, `commit-gate`, `readiness`, `python-launcher`,
`verify-tiers`.

Оценка: macOS ≈190 с под нагрузкой, Windows оператора ≈335 с (59 % предела). Всё остальное
(publisher, with-timeout ×2, merge-gate/gate/shell-grammar, module-resolution, finalize ×4, bd ×3,
complexity ×2, corpus, nonascii) переходит в full: `bash scripts/verify-reference.sh` — `/verify`
Developer после изменений (`.claude/rules/universal.md`) и обязательный CI `verify-reference`
перед merge. Merge-гейт не ослабляется; ослабляется только раннее локальное обнаружение для
инструментов, которые не участвуют в каждом коммите.

Windows-покрытие не теряется: джоба `windows-commit-tier` исполняет и commit tier, и остальные 22
шага прежнего commit tier (AC-03). Required check на `main` сейчас только Linux `verify-reference`;
сделать Windows/macOS required — настройка репозитория оператора (рекомендация PM в PR, не шаг
плана). `/finalize-pr` проверяет свежие checks текущего HEAD, включая Windows.

ADR: новая запись §3.38 меняет решение §3.37 о составе commit tier (§3.37 получает ссылку на
§3.38), с «Отклонёнными вариантами»; входит в PR до кода шага 6.

Отклонённые варианты (кратко, полностью — в ADR §3.38):

- *Оставить merge-gate/with-timeout в commit tier* — Windows оператора ≈540 с при пределе 570 с.
- *Параллельный запуск шагов* — тайминг-кейсы (`pre-bash-dispatch` быстрая фаза,
  `merge-gate-parse-budget`, complexity, `with-timeout-transparency`) станут флакать от
  собственной нагрузки; bash 3.2 на macOS без `wait -n`.
- *Ускорить `pre-bash-dispatch`* — отдельная работа с риском изменить смысл проверки.
- *Выбор тестов по изменённым файлам* — отклонено в §3.37, причины те же.

Named risk (принят PM, раскрыт в PR и ADR §3.38):

- быстрая фаза `pre-bash-dispatch` (≤ 10 с) флакает под сильной нагрузкой машины; тест остаётся
  в commit tier, флак гейта не устраняется этим PR;
- «ядро» уже реального пути коммита: `.claude/tools/with-timeout.sh` вызывается гейтом на каждом
  коммите, а `gate-*`/`shell-grammar-single-source` проверяют грамматику, общую с классификатором.
  Их регрессию локальный гейт не поймает — только `/verify` и CI (Linux full, Windows джоба).
  Merge-гейт не ослаблен;
- Windows-маршрут guard (шаг 2) добавляет запуск bash на каждый lookup: оценка ≈335 с
  пересчитывается по замеру после шага 2; при недостижимости бюджета — правило AC-05.

## Target → as-built → gap

| Surface | As-built (`b04b21c`) | Target |
|---|---|---|
| Guard: alias lookup при явном **репозиторном** контексте (`--git-dir`, `GIT_DIR`, `GIT_COMMON_DIR`, `-C`, `--work-tree`, `GIT_WORK_TREE`) | `git config --get alias.X` с недоступным `--git-dir`/`GIT_DIR`/`GIT_COMMON_DIR` возвращает 1 («нет alias»), guard пропускает команду — fail-open на любой ОС (macOS: `git --git-dir=/nonexistent/repo/.git outer` → rc 0). `-C`/`--work-tree` с недоступным путём уже дают 128 → block | Репозиторный контекст, который git не открывает (`git rev-parse --git-dir` с тем же контекстом ≠ 0), — блок (fail-closed) с понятной причиной. Контекст только из `-c`/`GIT_CONFIG_*`/`HOME`/`XDG_CONFIG_HOME` rev-parse-проверку не запускает (вне репозитория были бы ложные блоки) |
| Guard: пути Git Bash на Windows (D-7) | Нативный Python передаёт `/d/...` нативному `git.exe` без преобразования. Затронуты не только репозиторные пути, но и все пути источников конфигурации: `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM`, `HOME`, `XDG_CONFIG_HOME`, `-c include.path`/`includeIf.*.path`, `GIT_CONFIG_KEY_n/VALUE_n`, `--config-env`: недоступный путь git пропускает молча → lookup 1 → allow, а реальный запуск из Git Bash alias найдёт | На `os.name == 'nt'` alias lookup и rev-parse-проверка выполняются через Git Bash той же установки Git for Windows, что исполняет команды агента, с тем же argv и env (`bash -c 'exec git "$@"' _ <argv…>`, без сборки строки): MSYS-преобразование аргументов и env совпадает с реальным запуском, перечислять классы путей не нужно. Resolver Git Bash — собственный модуль guard (не тестовый `native_bash()`). Входы resolver — **только окружение процесса хука**: `CLAUDE_CODE_GIT_BASH_PATH` и PATH для поиска `git.exe` (присваивания перед командой, `env VAR=…`, `PATH=…` в команде на выбор не влияют; env команды передаётся только запущенному bash для git). Кандидат — `CLAUDE_CODE_GIT_BASH_PATH`, иначе `<git root>/bin/bash.exe` или `usr/bin/bash.exe` установки разрешённого `git.exe`. Решающий признак: bash и `git.exe` принадлежат одной установке Git for Windows (и для кандидата из `CLAUDE_CODE_GIT_BASH_PATH`); `uname -s` — только дополнительная проверка. WSL-заглушки (`System32`, `WindowsApps`), Cygwin, отдельный MSYS2, другая установка, неоднозначность, отсутствие, ошибка запуска → block |
| Python-тесты, запускающие `bash` (D-1) | `subprocess.run(['bash', …])` → WSL-заглушка | Все тесты reference-набора используют `native_bash()` (`scripts/tests/lib/claude_hooks.py`) или явный путь Git Bash |
| Symlink в фикстурах (D-2) | Фикстуры требуют привилегии symlink | Фикстуры, которым symlink не нужен по смыслу (fallback-bin), обходятся без него; кейсы, проверяющие отказ на symlink, при отсутствии привилегии дают явный SKIP с причиной и выполняются в Windows CI (runner с привилегией) |
| Кодировка (D-3) | `print('✓')` и чтение вывода по ANSI code page | Явный UTF-8 для собственного stdio тестов и дочерних процессов |
| Фикстуры PATH / gh / путь (D-4, D-5, D-6, D-8) | См. диагностику | Причина установлена RED на Windows и исправлена в фикстуре/скрипте; смысл проверки не меняется |

**Checkpoint-решения PM v0.7 (по отчёту Developer после шага 6).**

- **CP-1 `.claude/tools/publish-pr-comment.py` (runtime, разрешено).** Причина установлена в Windows
  CI: `_repository_root()` и другие чтения вывода git в publisher декодируют его по ANSI code page
  (`text=True` без `encoding`); на пути с кириллицей — `UnicodeDecodeError` (cp1252) или искажённый
  путь (cp1251) → publisher неработоспособен на Windows-проекте с кириллицей в пути. Изменение:
  все чтения вывода дочерних процессов в publisher — явный `encoding="utf-8", errors="strict"`;
  ошибка декодирования → прежний fail-closed отказ. Больше ничего в publisher не меняется (тело,
  фильтры, readiness-политика). AC-07.
- **CP-2 `scripts/tests/with-timeout.test.sh` (тест, SKIP разрешён узко).** Секции native-timeout и
  сигналов используют POSIX-семантику harness (`os.setpgid`, группы процессов, SIGINT/SIGHUP) и
  Popen `.sh` из нативного Python — на Windows не воспроизводимы. На `os.name == 'nt'`/MSYS эти
  секции дают явный SKIP с причиной; число пропусков печатается в итоге теста и в логе CI. Все
  остальные секции (fallback, аргументы, коды) обязаны PASS на Windows. Набор пропускаемых кейсов
  зафиксирован константой в тесте; на Windows фактический набор сверяется с ней (новый кейс не
  может молча уйти в SKIP). На Linux/macOS SKIP запрещён (тест это проверяет); единственное
  исключение — существующий SKIP «dash недоступен» (`with-timeout.test.sh:1082`), только при
  фактическом отсутствии `dash`, с причиной в выводе. Контракт кода `124` при истечении предела на
  Windows проверяется без SKIP (`with-timeout-transparency`). Named risk: семантика сигналов `.claude/tools/with-timeout.sh` на
  Windows автоматическим тестом не покрыта — раскрывается в ADR §3.38 и PR.
- **CP-3 `.claude/hooks/pre-bash.sh` `RESTORE_FILES` без кавычек вокруг корня** — вне scope, задача
  Beads `og-qr2`.
- **CP-4 guard (`check-repository-mutation.py`, файл уже в IN).** Тот же класс, что CP-1:
  `text=True` без `encoding` в `_current_branch`, alias lookup и rev-parse `_git_shell_context` →
  на Windows с кириллицей в пути проекта ложный блок (fail-closed). Изменение: явный
  `encoding="utf-8", errors="strict"`; ошибка декодирования → block (как сейчас). AC-02 edge.
- **Named risk — апостроф в пути на Windows.** MSYS не преобразует argv-путь с апострофом для
  нативных программ: у пользователя с апострофом в пути проекта или TEMP (`C:\Users\O'Brien\…`)
  часть скриптов получит непреобразованные `/d/...`. Guard не ослаблен (lookup и реальный запуск
  идут одним маршрутом). Раскрывается в ADR §3.38, CHANGELOG и PR; задача Beads.

Принятые отклонения реализации (подлежат Code Review): argv для lookup передаётся bash через
окружение и stdin-скрипт (`bash -s`, семантика `exec git "$@"`), а не командной строкой — MSYS сам
разбирает командную строку нативного родителя, и аргумент с апострофом мог бы спрятать `-C`
(fail-open); rev-parse только для `--git-dir`/`GIT_DIR`/`GIT_COMMON_DIR` (недоступные `-C`/
`--work-tree` git отвергает сам, 128); корень `TMPDIR` Windows CI без апострофа (кириллица и
пробел есть; апостроф остаётся в путях фикстур); `py -3` закреплён на 3.14 через `PY_PYTHON3`;
OSTYPE `cygwin` (Git Bash 5.3 из Git for Windows 2.56) принимается дополнительным фильтром —
решающий признак остаётся «bash и `git.exe` из одной установки Git for Windows»; Code Review
проверяет, что отдельный Cygwin по-прежнему блокируется проверкой установки.

## Шаги

1. **RED guard.** RED сейчас на macOS/Linux: недоступный `--git-dir`, `GIT_DIR`, `GIT_COMMON_DIR`
   с неизвестной подкомандой → block. Регрессионные (уже block): `-C`/`--work-tree` с недоступным
   путём. Не-блок: валидный контекст, builtin-подкоманды, `-c`/`HOME` вне репозитория.
2. **Guard fix.** Перед alias lookup при репозиторном контексте — `git rev-parse --git-dir` с тем же
   контекстом; отказ → GuardError (block). На `nt` alias lookup и rev-parse идут через resolver
   Git Bash guard (см. gap) как `bash -c 'exec git "$@"' _ <argv…>` с тем же env; resolver входит в
   замкнутое множество модулей guard, closure-тесты (`reference-closure`,
   `module-resolution-closure`) и distribution manifest. Таймаут lookup пересматривается по
   замеру Windows (запуск bash + git); превышение → block (fail-closed). Модульный тест маршрута
   `nt` и resolver (подмена `os.name`, кандидатов и launcher) + Windows CI по классам:
   `--git-dir`/`GIT_DIR`, `-C`, `GIT_CONFIG_GLOBAL`, `HOME`/`XDG_CONFIG_HOME`, `-c include.path`,
