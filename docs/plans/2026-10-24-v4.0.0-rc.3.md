# OverGate v4.0.0-rc.3 — план

**Цель:**
- проект без собственных overrides после fresh install или upgrade с rc.1/rc.2 побайтно (байты и mode) соответствует OverGate во всех managed- и settings-файлах;
- повторная установка идемпотентна;
- проект с overrides получает только необходимые изменения, без пересортировки файлов.

**Решение оператора 2026-10-24:** перед upgrade u2-lab выпустить `v4.0.0-rc.3` с исправлением
установщика. Нужно полное соответствие текущему OverGate, чтобы проверить его на реальном проекте.
Релиз — `prerelease=true`, `make_latest=false`.

Plan Review 1 использован (BLOCKED → v0.2, повторная проверка в той же сессии).

## 1. Target → as-built → gap

| # | Beads | Дефект `scripts/install-overgate.py` rc.2 | Цель |

| C1 | `og-48u` | `merge_settings` (строки 100–103) делает `setdefault('permissions').setdefault('deny')` для любого файла: `.codex/hooks.json` получает лишний `"permissions":{"deny":[]}` | `permissions` и его поля создаются только если они есть в source; project-owned ключи сохраняются |
| C2 | `og-dp6` | политика `ignore` (строки 123–126) дописывает фрагмент безусловно и переводит файл в LF | поведение по таблице §4.1 |
| C3 | `og-lnt` | `json_bytes` (строка 22) всегда сериализует с `sort_keys` | правило записи §4.2 |

Термины:
- «Source» — Git blob на exact source SHA, а не файл рабочего дерева: уже есть фикстура с CRLF source checkout.
- «Равно по смыслу» — строгое по типам равенство распарсенного JSON: сравниваются канонические `json.dumps(sort_keys=True)`, поэтому `true`, `1` и `1.0` различаются.

**Граница цели.** `merge_settings` переносит из source только hooks и `deny`. Поэтому байтовое
соответствие после upgrade гарантируется для баз rc.1 и rc.2, где settings source не менялись.
Для v3.9 → rc.3 цель не заявляется; это ограничение записывается в INSTALL и CHANGELOG.

## 4. Verification Contract

### 4.1 `.gitignore` (политика ignore), вход → ожидаемые байты

**Порядок:**
1. Удаляется legacy-строка `.codex/`.
2. Затем ищется блок фрагмента.

**Сравнение блока — построчно, без учёта EOL:** CRLF и LF равны, отсутствие перевода строки
после последней строки файла тоже не считается отличием. «Изменённое тело» — это отличие
содержимого строк.

| Вход | Ожидание |
|---|---|
| файла нет либо файл пуст (0 байт) — fresh | ровно байты фрагмента. Изменение поведения: в rc.2 было `\n\n` + фрагмент |
| фрагмент уже есть целым блоком в любом месте, в любом EOL | файл не меняется побайтно |
| заголовок `# OverGate personal state (managed fragment)` есть, тело блока отличается | `conflict: managed .gitignore fragment modified; resolve in target PR`, без записи |
| фрагмента нет | существующие байты сохраняются; если файл не кончается переводом строки — добавляется один; затем пустая строка и фрагмент. EOL вставки = EOL файла: CRLF, если все строки файла CRLF, иначе LF |
| строка `.codex/` (legacy v3.9) | удаляется ровно эта строка с её EOL; остальные байты сохраняются |

### 4.2 Settings (политика settings), правило записи

1. Результат merge по смыслу равен source → записываются байты source.
2. Иначе равен текущему target → байты target не меняются.
3. Иначе — детерминированная сериализация в порядке ключей target, где новые ключи идут
   следом, без `sort_keys`, `indent=2`, LF. Описано в INSTALL.

Новый conflict для изменённого фрагмента `.gitignore` ужесточает conflict-политику. В INSTALL
и CHANGELOG он описывается как новое поведение upgrade.
