# OverGate v4.0.0-rc.4 — план

**Целевая аудитория (оператор, 2026-10-24):** люди без опыта программирования, управления
проектами, тестирования и развёртывания. Агенты работают самостоятельно; человек ставит задачу,
принимает результат и нажимает merge. Запрос подтверждения на каждое действие такой аудитории не
помогает: она не может оценить, на что агент просит разрешение. Защита должна быть встроена в
процесс и не зависеть от суждения оператора.

**Цель:** коллега-неспециалист поручает агенту установить OverGate в свой проект по быстрому
старту. Агенты работают без вопросов, main защищён и локально, и на GitHub. Memory Bank и Beads
созданы и готовы к работе сразу после установки: без них агенты не ведут продукт автономно между
сессиями. Для разовых проектов есть режим без Beads. Windows и сложные пути проверены вживую.

**Решения оператора 2026-10-24:**
- режим агента в новом проекте — `auto` (классификатор Claude Code отсекает опасное без вопросов
  оператору); запасной вариант для аккаунтов без `auto` — флаг `--mode bypass`;
- защиту main на GitHub включает агент при установке;
- Memory Bank и Beads обязательны для автономной работы над продуктом: установка создаёт каркас
  Memory Bank и инициализирует Beads; режим `--no-beads` остаётся для разовых проектов, Memory Bank
  создаётся и в нём;
- при upgrade установка с неправленными settings (по смыслу равны известному прежнему source
  rc.1–rc.3) переводится на settings rc.4; settings с правками проекта сохраняют свой режим;
  og-1oh (артефакт rc.2 в конфиге Codex) закрывается тем же механизмом в WI-1;
- живую проверку на Windows выполняет оператор по чек-листу §5.4 на основном Windows-ПК разработки;
- og-7sr входит в rc.4.

**Повод:** пробная установка rc.2 на чистый проект и разбор готовности (сессия PM 2026-10-24).
Fresh install копирует рабочий `.claude/settings.json` эталона: `defaultMode: bypassPermissions`
отключает и встроенную страховку Claude Code; deny содержит остаток U2 `docker-compose.prod.yml`.
Хуки защищают main только в локальной сессии, на GitHub защиту никто не включает. Существующие
настройки проекта установщик сохраняет: проверено на проекте со своим `settings.json`.

**Режим:** CRITICAL. Установщик пишет permissions каждого установленного проекта; меняется
triage parser `finalize-pr` (pipeline governance, PM_ROLE §10).

## 2. Решения HOW

### 2.1 Режим агента (P1)

- Рабочие настройки эталона `.claude/settings.json` переходят на `defaultMode: auto`; deny-остаток
  U2 `docker-compose.prod.yml` удаляется. Fresh в проект без своих settings = байты source: rc.3
  AC-01 и правило записи rc.3 §4.2 сохраняются.
- Bypass-вариант — байты source с единственной текстовой заменой значения `defaultMode` на
  `bypassPermissions`. Прочие ключи не меняются: hooks не зависят от режима.
- «Известные» settings — канонические отпечатки (строгий по типам `json.dumps(sort_keys=True)`,
  как в rc.3): source rc.1–rc.3 (один blob `bf8f00d`), текущий source и его bypass-вариант.
  Хранятся в manifest.
- Install-state rc.4 хранит режим: `auto`, `bypass` или `custom` для settings с правками проекта.
  Install-state rc.1–rc.3 режима не содержит. Следующие RC добавляют source rc.4 и его
  bypass-вариант в известные; при upgrade без `--mode` сохраняется режим из install-state, а
  `custom` идёт по ветке «с правками».

Таблица решений:

| Settings в target | `--mode` не указан | `--mode` указан |
|---|---|---|
| файла нет (fresh) | source (`auto`) | выбранный вариант |
| = известный прежний source rc.1–rc.3 | source (`auto`); `plan` печатает смену режима | выбранный вариант; смена печатается |
| = текущий source или его bypass-вариант | no-op; режим в install-state приводится к факту файла | совпадает с файлом → no-op; отличается → выбранный вариант, смена печатается |
| с правками проекта, в том числе fresh в проект со своими settings | merge rc.3: permissions и `defaultMode` проекта не меняются, deny дополняется объединением; `plan` печатает «permissions проекта сохранены» | stop: «режим проекта со своими settings меняется вручную в target PR» |

- Доступность `auto` зависит от аккаунта и версии Claude Code, установщик её не проверяет.
  QUICKSTART и INSTALL объясняют, как понять, что `auto` недоступен, и как перейти на
  `--mode bypass`. Фактическое поведение Claude Code фиксируется в AC-05 (R1).
- Codex (og-1oh). Артефакт оставляют установщики rc.1 и rc.2 (один blob `040a85e`) при любом
  повторном запуске поверх `.codex/hooks.json`. Точная форма снятия:
  - `permissions == {"deny": []}` → ключ `permissions` удаляется;
  - в `permissions` есть другие ключи → удаляется только пустой `deny`.
  Затем правило записи rc.3: результат по смыслу равен source → байты source. Custom-ключи Codex
  сохраняются.

### 2.2 Защита main на GitHub (P2)

Helper `scripts/og-protect-main.sh` (managed, вне Beads-набора), запуск
`bash scripts/og-protect-main.sh`. Исходы определяются по данным, а не по HTTP-коду:

| Шаг | Проверка | Исход |
|---|---|---|
| 1 | `gh auth status` неуспешен | код 3 «пропущено: нет gh auth» |
| 2 | `GET /repos/{o}/{r}`: `permissions.admin` false | код 2 «нет прав» |
| 3 | `GET …/branches/{b}`: `protected` false → `PUT …/protection` | ответ 403 о тарифе (приватный репозиторий на бесплатном плане) → код 4 «недоступно на тарифе» |
| 4 | classic-защита есть | недостающие правила добавляются, существующие не снимаются, в том числе `enforce_admins`; всё уже есть → no-op |
| 4а | `protected: true`, но classic `GET …/protection` → 404 (ветку защищает ruleset) | ruleset не меняется; код 5 «защищено ruleset», строка в PR с просьбой сверить правила |
| 5 | проверка чтением | `protected`, PR обязателен, `enforce_admins.enabled == true`, force push и удаление запрещены → код 0; не сошлось → код 6 |

- Правила: PR обязателен (0 approvals — оператор один), `enforce_admins: true` (агент работает под
  аккаунтом оператора-администратора; без этого прямой push в main на GitHub пройдёт),
  `allow_force_pushes: false`, `allow_deletions: false`.
- Коды 2, 3, 4 и 5: установка продолжается, строка в target PR; в Memory Bank строка R8 пишется
  только в уже созданный каркас (порядок helpers — §2.3). Код 6 — stop.
- Агент-установщик проверяет `gh auth status` ещё до `plan`. Нет авторизации, а target PR открыт
  через коннектор → защита пропускается (код 3), это записывается в target PR.
- Агент-установщик запускает helper после `apply`, когда main уже есть на GitHub. Поручение
  оператора на установку — подтверждение этой удалённой записи (ADR 3.29); фиксируется в §3.33.
- Guard `check-repository-mutation` не видит `gh` внутри `bash scripts/…` и пропускает helper.
  `--method PUT/DELETE` на `…/protection` вне helper проходит guard и deny (og-9ic.10, R7).

### 2.3 Memory Bank и Beads при установке (P3)

**Порядок helpers после `apply`** (фиксирован, записывается в INSTALL и QUICKSTART):
`og-init-memory-bank.sh` → `bd-bootstrap.sh` (кроме `--no-beads`) → `og-protect-main.sh`. Любые
записи в Memory Bank, в том числе строка R8, делаются только после создания каркаса.

**Memory Bank** создаёт helper после `apply`, а не manifest. `safe()` установщика запрещает
managed-пути `.memory-bank` и `.beads`, и этот запрет не меняется; rollback Memory Bank не трогает.
- Шаблоны `.agents/templates/memory-bank/` (managed): `projectbrief`, `productContext`,
  `systemPatterns`, `techContext`, `activeContext`, `progress` — заголовки и подсказки.
- Helper `scripts/og-init-memory-bank.sh` (managed, вне Beads-набора): каталога `.memory-bank/`
  нет → создаёт шесть файлов из шаблонов; каталог есть, даже частичный → no-op, отчёт перечисляет
  отсутствующие файлы, файлы проекта не трогаются.
- Запускается при fresh и при upgrade (установка rc.3 без Memory Bank получает каркас), в том
  числе в `--no-beads`.
- AGENTS template: строка про Memory Bank — читать перед задачей, обновлять `activeContext` и
  `progress`. ADR §3.6 говорит о пяти файлах; §3.33 фиксирует шесть, как в Memory Bank OverGate.

**Beads** инициализирует helper `scripts/bd-bootstrap.sh` (Beads-набор, managed), запуск
`bash scripts/bd-bootstrap.sh` после `apply`:
1. вне основного checkout (`bd_env_assert_main_checkout`) → stop до любого вызова bd;
2. `bd` нет → stop с инструкцией установки для ОС; helper ничего не скачивает;
3. версия bd вне диапазона из manifest → stop (R9);
4. база уже есть (`.beads/metadata.json`) → проверка постусловия; нет `origin/beads-backup` →
   шаг 7; иначе no-op;
5. иначе `bd init` без генерации agent-инструкций (v3.9: `--skip-agents`), embedded-режим;
6. конфигурация: `export.auto=false`, `backup.git-push=false`, `sync.remote` не задан, Dolt-remote
   удалён (v3.9 §B.5: без этого bd пытается auto-push в origin/main);
7. первый `bash scripts/bd-sync-export.sh` создаёт ветку `beads-backup`.

Постусловие (проверяется на шагах 4 и 7): конфигурация шага 6, успешный `bd ready --json` и
существующая ветка `origin/beads-backup`.
Fail-closed на любом шаге, без `--force`. Флаги сверяются с `bd --help` поддерживаемого диапазона
версий в основном checkout тестового проекта, не в worktree.

### 2.4 Режим `--no-beads` (P4)

- Manifest: у Beads-entries (8 из rc.2 и `bd-bootstrap.sh`) поле `"component": "beads"`;
  `--no-beads` их исключает. Memory Bank создаётся (§2.3).
- Режим входит в plan JSON (`apply` пересобирает план и сравнивает). `validate_payload` строит
  проекцию payload по режиму и передаёт режим checker'у; CLOSURE-002 проверяет только entries
  выбранного режима. Отсутствующий или нечитаемый install-state = `beads: true` (fail-closed).
- AGENTS template: Beads-абзац между маркерами `<!-- overgate:beads -->` и
  `<!-- /overgate:beads -->`; в `--no-beads` блок вместе с маркерами не пишется.
- Deny `bd delete*`, `bd dolt push*` и прочие остаются: в проекте без bd они безвредны.
- `check-reference.py` в target: Beads-пути обязательны только при `beads: true`.
- Upgrade: режим берётся из install-state; смена режима — stop. Install-state rc.1–rc.3 = `beads: true`.

**Triage `defer` в `finalize-pr`:**
- Beads ID — как сейчас: форма и существование.
- ID трекера принимается только при `beads: false` в install-state. Формы: `#[1-9][0-9]*` и
  `https://github.com/<owner>/<repo>/issues/<N>` только для репозитория этого PR.
- Существование и состояние проверяет `gh issue view`: это issue, а не PR, и он открыт. `gh`
  недоступен → stop, как сейчас при «проверить нечем».
- При `beads: true` любая форма ID трекера → stop. Отсутствующий или нечитаемый install-state
  для `finalize-pr` тоже означает `beads: true`.
- По PM_ROLE §10 WI-1 финализируется доверенной версией `finalize-pr` (§0, AC-16).

### 2.5 install-state и rollback (P5)

- Tracked: source SHA, версия manifest, режим агента, режим Beads, относительные target-пути, хеши.
  Абсолютных путей нет. Абсолютный путь backup — только в ignored
  `.overgate-backups/<id>/rollback.json`; `rollback` принимает `--backup` явно.
- Upgrade читает install-state rc.1–rc.3 с абсолютными путями и пишет новый формат.
- Rollback сохраняет семантику rc.3 «всё или ничего»: файл журнала, изменённый после `apply`, —
  drift и STOP. Rollback допустим сразу после `apply`, до helpers и правок (`verify.sh`, Memory
  Bank). После них откат — revert install PR в target.
- Rollback возвращает managed-байты, settings и install-state как до установки: после fresh
  install-state отсутствует, после upgrade — побайтно прежний, в том числе с абсолютными путями
  rc.1–rc.3. Memory Bank, база Beads, `beads-backup` и защиту main rollback не снимает (§6).

### 2.6 `QUICKSTART.md` (P6)

Файл в корне эталона, в manifest не входит. Не длиннее 150 строк, написан для человека без опыта
программирования; термины поясняются при первом упоминании. Разделы:
- для кого: один оператор на проект, Claude Code; Windows (Git Bash), macOS, Linux; агенты
  работают сами, человек ставит задачу, принимает результат и нажимает merge;
- что понадобится и как проверить;
- одна фраза-поручение агенту на установку. Агент сам:
  - если репозитория нет — создаёт его с первым коммитом в main (например, с README) без push
    агента в main;
  - открывает target Draft PR и план установки; `PLAN_READY` выдаёт отдельный reviewer-агент, а не
    установщик (INSTALL: approval — не самоутверждение);
  - выполняет `apply` и helpers, заполняет `.agents/project/verify.sh` тестами проекта (если тестов
    нет — создаёт минимальные);
- режим `auto` и запасной `--mode bypass`; `--no-beads` для разовых проектов;
- что появится в проекте и зачем;
- первый PR на примере FAST-задачи: задача → план → реализация → проверка → finalize → merge;
- откат и известные ограничения.

### 5.2 Инварианты

- conflict-политика, порядок операций, backup и rollback «всё или ничего» не ослабляются; нет `--force`;
- `safe()` по-прежнему запрещает managed-пути `.memory-bank` и `.beads`;
- permissions и mode проекта со своими settings не меняются ни в каком режиме;
- hooks одинаковы во всех режимах: защита не зависит от режима агента;
- helpers не ослабляют существующую защиту main и не перезаписывают существующую базу Beads или
  Memory Bank.

### 5.3 Named risks

- R1 — `auto` недоступен на аккаунте коллеги: агент упирается в вопросы или ошибку (AC-05;
  QUICKSTART объясняет переход на `--mode bypass`).
- R2 — settings с правками проекта ошибочно признаны «известными» и перезаписаны: потеря project
  allow/env (AC-03, AC-04; строгий по типам отпечаток).
- R3 — ослабление triage parser `finalize-pr`: `defer` с мусором или чужим issue проходит (AC-11);
  самосертификация исключена доверенной версией гейта (AC-16, og-159).
- R4 — `--no-beads` ломает хуки или скиллы, которые ждут bd (AC-09; хуки и tools bd не вызывают).
- R5 — новый формат install-state ломает upgrade или rollback (AC-04, AC-12).
- R6 — классификатор `auto` блокирует штатные действия пайплайна или helpers (AC-05). При блоке —
  запись в PR и решение оператора.
- R7 — агент снимает или ослабляет защиту main через `gh api --method PUT/DELETE`: это проходит
  guard и deny (og-9ic.10, вне WI-1). `enforce_admins` защищает от push, но не от снятия защиты.
  Code Review проверяет, что helper — единственная запись защиты в пакете.
- R8 — защита недоступна на тарифе (приватный репозиторий на бесплатном плане): гарантия «merge
  только оператор» остаётся локальной. Явная запись в target PR, Memory Bank и QUICKSTART (AC-06).
- R9 — изменение CLI bd ломает bootstrap: диапазон версий, fail-closed (AC-08).
- R10 — смена режима при upgrade на `auto` у аккаунта без `auto` останавливает агентов (AC-04, R1):
  `plan` печатает смену режима, QUICKSTART и INSTALL объясняют `--mode bypass`.

## 6. Rollback

Revert PR до релиза. После публикации — отзыв в описании release и rc.5; тег не двигать.

Проект, установленный rc.4, откатывается `install-overgate.py rollback` только сразу после `apply`,
до helpers и правок: семантика «всё или ничего» rc.3, журнал хранит прежние байты settings и
install-state. После helpers или правок (`verify.sh`, Memory Bank) откат — revert install PR в
target. Memory Bank, базу Beads, ветку `beads-backup` и защиту main rollback не снимает: это
отдельное решение в target PR.
