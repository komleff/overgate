# Сохранение работающего Beads при обновлении OverGate

Сотрудник обновляет OverGate в рабочей ветке проекта, продолжает видеть свои задачи и может вернуться к прежней версии инструментов. После отката сохраняются в том числе задачи, опубликованные коллегами за это время. План выпуска ведёт PM линии Slipstream (U2-m08dg). Дефект обнаружен в [OverStudio #30](https://github.com/komleff/overstudio/pull/30#issuecomment-7068085765).

## Исходное состояние и границы

База OverGate — RC1, `596f07b468aeb9423148f587bf5e9fa77ae57566`. В OverStudio установлен source `769ddc4251861641fa3ab2c9d6a4014a75f8d7c3`, режим `auto`, протокол `managed-v1`, префикс `overstudio`. У проекта зарегистрирован отдельный publisher и уже опубликованы снимок, маркер managed и журнал выполненных операций. В [инвентаре RC1](https://github.com/komleff/overstudio/pull/30#issuecomment-7067949483) 23 изменения и 0 файловых конфликтов.

В `scripts/install-overgate.py` функция `make_plan` допускает пакет сохранения для legacy, `apply` требует его для существующего состояния, а `rollback` ожидает отсутствующую удалённую ветку для обычной managed-установки. Меняется один маршрут: обновление ранее установленного и уже активированного managed-проекта с тем же протоколом. Сохраняются прежние правила для новой установки, отключённого Beads, перехода с legacy и старых журналов отката. Владельцем данных и единственной точкой записи задач остаётся действующий publisher.

## Реализация

1. В текущем установщике выделить подтверждённый случай managed → managed. Взять исходное состояние установки из прежней поставки, проверить настоящую локальную регистрацию, общий origin, префикс и состояние доверенного publisher. Прочитать изолированно по точному SHA удалённой ветки R действительные snapshot, ledger и marker с проверкой штатным валидатором истории. Связать доказательство с target/веткой, source, прежним install-state, регистрацией и контрактом в существующем плане; отдельный legacy-пакет для этого маршрута не нужен. При неизвестном remote, повреждении, подмене регистрации или недоказанном протоколе вернуть причину до записи.
2. В `apply` сохранить привязку к точным байтам одобренного плана и повторное построение до записи. Если между планом и применением изменились R, входные файлы или регистрация, нужен свежий план. Записывать только установочные файлы и install-state в рабочем дереве target. Данные трекера, очереди, квитанции, настройки регистрации и отдельный checkout publisher остаются у их владельцев. Совместить операции над одним target так, чтобы параллельные apply/rollback не смешивали резервные копии. При отказе сохранить исходные данные и пригодный путь восстановления.
3. В журнале для этого маршрута различать обновление и первую установку. Связать before/after состояния, список управляемых файлов, их байты и режимы с целевым проектом и проверенным источником. Перед откатом подтвердить старый и текущий managed-протокол, регистрацию, целостность журнала и отсутствие локальных изменений в восстанавливаемых файлах. Разрешить прежний R или доказанное штатное продвижение от R с тем же префиксом. Откатить только поставку, не перематывать ветку задач. Старые журналы по-прежнему обрабатываются по прежним правилам. После слияния кода проекта возврат оформляется обратным PR.
4. В существующих `scripts/tests/install-distribution.test.py` и тестах managed Beads использовать отдельные target, доверенный publisher, peer и тестовый origin. В `.agents/INSTALL.md` описать штатный маршрут, отказ и откат. Включить RC2 в версию манифеста и существующие release metadata до финальной проверки; реализация, QA и scoped Code Review идут после одобрения этого плана.

## Приёмка

| ID | Опыт | Ожидаемый результат |
|---|---|---|
| M1 | На предыдущей работающей установке подготовить и применить план. В fixture есть действующая регистрация, история нескольких задач, журнал операций и проектный адаптер. | Проверка из другого checkout подтверждает прежний R и исходные объекты. Сохранены регистрация, префикс, параметры доступа, проектные файлы и работоспособность адаптера. Повторный plan не предлагает новых изменений содержимого. |
| M2 | В fixture после upgrade опубликовать задачу прежним доверенным publisher. Выполнить rollback. Через прежний publisher провести ещё одну штатную операцию, затем прочитать из peer. Повторить rollback в отдельном случае без продвижения R. | После отката восстановлены исходные bytes/modes и install-state. Новая задача, её ID и история видны, повтор операции не дублируется. Ни apply, ни rollback не создают task-коммита. |
| M3 | По одному менять существенный вход: недоступный или другой origin, изменённый prefix/регистрация, пропавший marker, разрыв истории, движение R перед apply, изменённый управляемый файл перед rollback, конфликт двух установщиков. | Нештатное состояние даёт адресный отказ до записи. При сбое в середине операции проверяются восстановление или штатное продолжение на сохранённом журнале, а также целостность проектных данных и задач. |
| M4 | Прогнать существующие сценарии fresh managed, legacy → managed, Beads off, проектные overrides и предыдущий формат rollback-журнала. | Сохраняются действующие гарантии, в частности прежний запрет отката первой установки после появления задач. |
| M5 | На изолированной копии OverStudio воспроизвести состав реального проекта и его зарегистрированного publisher, с отключённой записью в рабочий origin. Отдельный локальный remote принимает тестовые записи. Сделать plan/apply/replan/rollback и вызвать проектный адаптер. | В отчёте есть SHA source и target, R до/после, сравнение файлов и статусы чтения, публикации и отката. Проверены `AGENTS.md`, `.agents/project/verify.sh`, Memory Bank, пользовательские настройки и проектные материалы по OG5-02/03/05. |

## Выпуск и пилот

Кандидат допускается к выпуску после M1–M5, независимого QA по сохранности, адресного ревью изменившегося кода и штатного CI на финальном дереве, включая Windows и Linux. Прогон на macOS именуется нативным только по фактическому результату macOS. Планируется отдельный prerelease `v5.0.0-rc.2`. Оператор выполняет merge и принимает решение о публикации. Стабильный канал — Delivery First 4.0.0.

После публикации обновить существующий OverStudio #30 на точный опубликованный SHA и актуальную базу, заново снять инвентарь и получить PLAN_READY target-ревью. Проверить изолированный откат и пользовательские файлы. После операторского merge синхронизировать только код зарегистрированного publisher по принятому в проекте порядку, проверить чтение задач и очередную штатную публикацию. Работающие задачи, их префикс и учётные данные сохраняются.
