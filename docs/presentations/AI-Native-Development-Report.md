# AI-Native Development — паттерны и опыт команды ИИ-агентов

> **О документе.** Изначально — план доклада об опыте разработки конкретного игрового проекта
> (`slime-arena`, первая зрелая реализация этого пайплайна, см. `.agents/REFERENCES.md`) с
> оператором-нетехнарём и командой ИИ-агентов. Здесь материал обобщён: метрики, технологический
> стек и имена конкретных файлов убраны или явно помечены как исторический пример. Актуальная
> ролевая модель и команды живут в `.agents/AGENT_ROLES.md`, `.agents/PM_ROLE.md`,
> `.agents/PIPELINE.md` — при расхождении с этим документом прав канон, не история.
> Используй документ как reference-материал для собственного доклада о твоём AI-Native проекте:
> подставляй свои метрики и примеры в те же разделы.

## Контекст

**Главный вопрос, на который отвечает такой доклад:** можно ли разработать production-ready
продукт силами команды ИИ-агентов, где человек — продакт-менеджер без технического бэкграунда,
принимающий решения на основе вердиктов (APPROVED/CHANGES_REQUESTED), а не чтения кода?

### Что стоит собрать перед докладом (по своему проекту)

- **Масштаб:** период разработки, число коммитов и их динамика в день, доля коммитов с участием
  ИИ, объём кода и тестов (production/test ratio — сильный сигнал зрелости для AI-Native кода),
  объём документации.
- **Технологический стек** — коротко, не для похвальбы, а чтобы аудитория понимала домен.
- **Ролевая модель агентов**, использованная в проекте, и её версия на момент доклада —
  ролевые схемы AI-Native пайплайнов быстро эволюционируют между проектами.
- **Уникальные инфраструктурные паттерны**, которые сложились в проекте (см. раздел
  «Инфраструктура и процессы» ниже — это ядро, которое стоит раскрыть подробно).

## Структура доклада

### 1. Введение (3 мин)

**Тезисы:**
- Проект разрабатывается **исключительно** ИИ-агентами.
- Оператор — продакт-менеджер, необязательно с техническим бэкграундом.
- **Главный вопрос:** можно ли разработать production-ready продукт только с ИИ?

**Темы для обсуждения:**
- Как аудитория относится к идее «non-technical PM управляет ИИ-командой»?
- Какие риски видят в таком подходе?

### 2. Масштаб проекта (5 мин)

**Тезисы (заполни своими данными):**
- Период от первого коммита до релиз-готовности.
- Объём кода и тестов, соотношение production/test — высокая доля тестов (у первой зрелой
  реализации этого пайплайна тесты составляли больше половины кодовой базы) обычно означает,
  что Zero Trust к коду компенсируется автоматической проверкой, а не читается вручную.
- Пиковая скорость коммитов — полезный индикатор интенсивности параллельной работы агентов.
- Объём и версионирование документации.

**Визуализация:**
- График активности коммитов по дням.
- Соотношение production/test кода (диаграмма).
- Breakdown по модулям (client/server/shared/docs — адаптируй под свою структуру).

**Темы для обсуждения:**
- Сравнение с типичным временем на MVP в командах людей.
- Реалистичны ли такие цифры для человеческой команды сравнимого размера?

### 3. Архитектура команды агентов (7 мин)

**Тезисы:**
- Ролевая модель со **строгим разделением ответственности** — ключевой паттерн, повторяющийся
  во всех зрелых реализациях этого пайплайна. Актуальный набор ролей и их обязанности —
  `.agents/AGENT_ROLES.md`; в разных проектах роли называются и делятся по-разному (например,
  ранние реализации разносили Architect/Art Director/Developer/Reviewer/Session Manager,
  текущая модель overgate строится вокруг PM/Developer/Reviewer/Tester/Planner/Doc Sync),
  но принцип один: каждая роль не может делать работу, которая требует независимой проверки
  другой ролью.
- **Zero Trust:** оператор не проверяет код технически — решения принимаются на основе
  вердиктов агентов и автотестов, см. `.claude/rules/universal.md` / `.agents/AGENT_ROLES.md`.
- **Бинарный контроль:** только `APPROVED` / `CHANGES_REQUESTED`, без промежуточных состояний,
  которые вынуждали бы оператора вникать в детали.

**Обобщённый workflow цикла задачи** (адаптируй под свою ролевую модель):
```
Planner/Architect → создаёт задачу в трекере (Beads)
Developer          → берёт задачу, реализует код, открывает PR
Reviewer            → проверяет, выносит вердикт
(опционально)       → второй Reviewer на другой модели — кросс-модельное ревью
PM/Session Manager  → синхронизация состояния, обновление Memory Bank
Оператор            → merge PR (обычно единственное техническое действие человека)
```

**Темы для обсуждения:**
- Как распределены роли в командах аудитории?
- Готовы ли доверить merge без ручного code review?
- Что произойдёт, если у Developer появится доступ к созданию задач самому себе?

### 4. Инфраструктура и процессы (8 мин)

Это ядро доклада — паттерны здесь переносятся между проектами почти без изменений.

#### 4.1 AI-native task tracker (в этом пайплайне — Beads)

**Почему не JIRA/Asana:**
- CLI-интерфейс, удобный для агента, а не для человека с мышью.
- Интеграция с git — трекер синхронизируется вместе с кодом, а не живёт отдельной жизнью.
- Явные зависимости между задачами, которые агент может обходить программно.
- Базовые команды: `bd ready` (что можно брать в работу), `bd show <id>`, `bd update`, `bd close`.
- Подробности и правила эксплуатации — `.claude/rules/beads.md` (если сгенерирован из
  `.agents/INSTALL.md`) и `.agents/PIPELINE.md`.

#### 4.2 Memory Bank — внешняя память между сессиями

**Проблема:** у агента нет памяти между сессиями — контекст обнуляется при каждом новом старте.

**Решение:** Markdown-файлы как «долговременная память» проекта, читаемые по ролям (lazy
loading — каждая роль читает только нужные файлы, не весь банк целиком). Актуальная структура
и состав файлов — `.agents/PIPELINE.md` и `.agents/AGENT_ROLES.md`; состав со временем растёт
(например, добавляются `systemPatterns.md`, `productContext.md`), не привязывайся к фиксированному
списку из четырёх файлов — сверяйся с текущей структурой своего проекта.

**Общий принцип структуры:**
```
<каталог памяти>/
├── activeContext.md      → что происходит СЕЙЧАС
├── progress.md           → что ЗАВЕРШЕНО
├── systemPatterns.md     → КАК построена архитектура
└── ...                   → остальные файлы по мере роста проекта
```

#### 4.3 Протокол завершения сессии («Landing the Plane»)

**Критичный протокол**, без которого работа между сессиями теряется:
1. Создать задачи для оставшейся работы (не оставлять её «в голове» агента).
2. Прогнать quality gates (тесты, линтеры, документационные гейты).
3. Обновить статусы задач в трекере.
4. **Обязательно:** зафиксировать изменения в git и убедиться, что они синхронизированы с
   удалённым репозиторием.
5. Обновить Memory Bank.

**Гарантия:** следующая сессия (тот же агент или другой) не начинает с нуля.

**Темы для обсуждения:**
- Как аудитория управляет контекстом в своих проектах?
- Сталкивались ли с потерей информации при переключении задач/людей?
- Применим ли Memory Bank к человеческим командам (онбординг, handoff)?

### 5. Качество и тестируемость (7 мин)

Раздел про технические достижения в первоисточнике был сильно привязан к специфике одной игры
(детерминизм симуляции, размер mobile-бандла). Обобщённая версия — какие категории качества
стоит измерять и предъявлять в докладе:

- **Детерминизм/воспроизводимость** там, где это критично для домена (симуляции, финансовые
  расчёты) — как гарантируется тестами, а не ревью «на глаз».
- **Производительность/размер** там, где это ограничение продукта (мобильный бандл, задержка
  сети) — с измеримым до/после.
- **Нагрузочное тестирование**, если продукт многопользовательский.
- **Доля прохождения интеграционных тестов** и что именно они покрывают.

**Темы для обсуждения:**
- Удивляет ли аудиторию качество кода, написанного ИИ?
- Как оценивать высокое соотношение production/test кода — избыточность или норма для
  Zero Trust к разработке?
- Можно ли доверять ИИ критичные для домена части системы?

### 6. Документация (5 мин)

#### Объём и структура (заполни своими цифрами)
- Число Markdown-файлов, строк в ключевых пакетах документации.
- Модульная структура (например, GDD-пакет из нескольких файлов с версионированием).

#### Качество документации
- Версионирование критичных документов.
- Явная нотация требований (`[MUST]`, `[SHOULD]`, `[MAY]` или аналог).
- Глоссарий в архитектурных документах.
- Диаграммы (Mermaid, ASCII) там, где текст не читается быстро.

**Темы для обсуждения:**
- Как обстоят дела с документацией в проектах аудитории?
- Кто обычно пишет и поддерживает документацию у людей?
- Решает ли ИИ-агент проблему «устаревшей документации» — или создаёт свою версию той же
  проблемы (документ противоречит коду, потому что агент его не синхронизировал)?

### 7. Challenges и Lessons Learned (8 мин)

Самый ценный раздел доклада — обобщённые паттерны сохраняются между проектами.

#### 7.1 Технические вызовы

**God Objects:**
- Один файл/модуль стягивает на себя слишком много ответственности за счёт того, что агенту
  проще дописать в существующий файл, чем декомпозировать.
- Решение: явная декомпозиция на более мелкие системы/модули как отдельная задача, а не
  побочный эффект следующей фичи.

**Домен-специфичные инварианты** (детерминизм, консистентность состояния и т.п.):
- Риск: источник недетерминизма/некорректности незаметно проникает в код через удобный,
  но запрещённый API (например, обращение к системным часам или генератору случайных чисел
  напрямую вместо контролируемой обёртки).
- Решение: автотесты и/или архитектурные гейты на каждом PR, а не полагание на память агента
  о правиле.

#### 7.2 Процессные вызовы

**Context switching:**
- Агенты не помнят состояние между сессиями.
- Решение: Memory Bank (раздел 4.2).

**Scope creep:**
- Роль-исполнитель расширяет задачу за рамки исходных требований (по инициативе, не по злому
  умыслу — агент «видит» соседнюю проблему и чинит заодно).
- Решение: явное правило «одна задача = один фокус», проверяемое ревьюером.

**Merge conflicts / гонки при параллельной работе:**
- Несколько агентов работают параллельно над связанными частями.
- Решение: PR workflow с человеком (или единственным координирующим агентом) на merge.

#### 7.3 Успешные паттерны

- **Структурированные commit-сообщения** (`feat:`, `fix:`, `refactor:` — или своя конвенция).
- **Co-Authored-By** в коммитах — прозрачность вклада ИИ, полезно и для аудита, и для этики.
- **Строгое разделение ролей** — минимизирует конфликты интересов внутри одной сессии.

**Темы для обсуждения:**
- С какими проблемами аудитория сталкивалась при внедрении ИИ-инструментов?
- Какие из этих паттернов применимы к их проектам?
- Как они контролируют scope в задачах у людей — и работает ли это лучше или хуже?

### 8. Эффективность и сравнение (7 мин)

#### Количественные показатели
Заполни своими метриками: коммитов за период, доля с участием ИИ, пиковая производительность.

#### Сравнение с традиционной разработкой (шаблон таблицы)

| Аспект | Традиционная | AI-Native |
|--------|--------------|-----------|
| **Команда** | 5–15 человек | 1 оператор + агенты |
| **Время до MVP** | месяцы–годы | недели |
| **Code review** | человек читает diff | агенты + автотесты |
| **Документация** | часто устаревает | обновляется агентами вместе с кодом (при дисциплине) |
| **Task tracking** | JIRA, Asana | AI-native трекер (CLI, git-интеграция) |
| **Затраты** | пропорциональны штату | пропорциональны API-использованию |

**Темы для обсуждения:**
- Насколько реалистична декларируемая экономия времени/денег — и за счёт чего именно она
  достигается (меньше синхронизаций, отсутствие простоя, параллелизация ролей)?
- Где AI-Native подход **не** применим (safety-critical, жёсткий compliance)?
- Готова ли аудитория доверить ИИ основную долю разработки?

### 9. Roadmap: следующий шаг автоматизации (5 мин)

#### Типичное текущее состояние
- Оператор выполняет роль «диспетчера» между агентами и мержит финальный результат — это
  часто единственное оставшееся техническое действие человека.

#### Типичное направление развития
- Оркестрация очереди задач: диспетчер задач → пул агентов-исполнителей → пул ревьюеров →
  автоматический merge при выполнении критерия консенсуса (например, N независимых
  `APPROVED`-вердиктов от разных моделей).
- Целевая метрика — время полного цикла задачи без участия человека.

**Темы для обсуждения:**
- Насколько автономными должны быть агенты в проектах аудитории?
- Где проходит граница — 50% автономии? 90%? 100%?
- Нужен ли «kill switch» для полностью автономных агентов?

### 10. Применимость и этика (5 мин)

#### Подходит для:
- MVP/прототипы для валидации идеи.
- Стартапы с ограниченным бюджетом.
- Проекты малого/среднего масштаба.
- Поддержка legacy-проектов.

#### Требует адаптации:
- Enterprise-проекты (security, compliance).
- Высоконагруженные системы с жёсткими SLA.

#### Не подходит (или требует существенно иного контроля):
- Safety-critical системы (авиация, медицина).
- Домены с нулевой толерантностью к ошибкам.

#### Этические вопросы:
- Что происходит с ролью разработчиков-людей?
- Кто несёт ответственность за баги, произведённые ИИ-агентом?
- Как определяется авторство кода — человек или ИИ, и имеет ли это значение?

**Темы для обсуждения:**
- Как AI-Native разработка может изменить индустрию?
- Какие роли останутся за людьми через несколько лет?
- Нужны ли новые стандарты и сертификации для AI-generated кода?

### 11. Выводы и вопросы (5 мин)

#### Инсайты, которые обычно подтверждаются на практике:
1. **Внешняя память (Memory Bank) критична** для непрерывности AI-Native разработки.
2. **AI-native трекер задач эффективнее** классических таск-трекеров, рассчитанных на людей.
3. **Строгое разделение ролей** минимизирует конфликты интересов и ошибки самопроверки.
4. **Zero Trust к коду работает** только при наличии сильного автоматического контроля
   (тесты, гейты) — без него это просто отказ от контроля.
5. **Протокол завершения сессии** («Landing the Plane») гарантирует непрерывность между
   сессиями и агентами.

#### Открытые вопросы для аудитории:
1. Готовы ли попробовать AI-Native разработку в своих проектах?
2. Какие барьеры видят для внедрения?
3. Как изменится роль PM/Product Owner в AI-Native командах?
4. Нужны ли новые инструменты и фреймворки для управления ИИ-агентами?

## Как использовать этот материал

### Материалы для подготовки своего доклада

**Визуализации:**
1. График коммитов по дням за период разработки.
2. Pie chart: распределение кода по модулям (client/server/shared/tests/docs).
3. Workflow diagram: цикл задачи от постановки до merge.
4. Architecture diagram: оркестрация задач (текущая или целевая).
5. Timeline: ключевые вехи разработки.

**Демо (по возможности):**
- Живой продукт, если доступен для показа.
- Скриншоты ключевых экранов/интерфейсов.
- Пример коммита с `Co-Authored-By`.
- CLI трекера задач в действии.

**Раздаточные материалы:**
- Инфографика с метриками проекта (1 страница).
- Comparison table: Traditional vs AI-Native (1 страница).
- Ссылка на репозиторий/демо, если доступны.

**Критичные файлы для справки** (адаптируй пути под свой проект):
- `.agents/AGENT_ROLES.md` — актуальные роли агентов.
- `.memory-bank/activeContext.md` — текущее состояние проекта.
- Ключевые спеки/ТЗ релиза.
- Архитектурная документация верхнего уровня.

**Git-статистика для сбора метрик:**
```bash
# Общее количество коммитов
git log --oneline | wc -l

# Коммиты с участием конкретной модели/агента
git log --grep="Co-Authored-By: <имя модели>" --oneline | wc -l

# Активность по дням
git log --format="%ad" --date=short | sort | uniq -c

# Топ-авторы
git shortlog -sn
```
